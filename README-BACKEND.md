# Backend Lumo — état au 11 octobre 2026

Le schéma de `supabase.sql` est **déjà appliqué** au projet Supabase `mxfgtcubzdhkmtcyqznp` (migrations `lumo_secure_clubs_and_notifications`, puis correction `lumo_validate_pool_aliases`). Ce fichier remplace l'ancien schéma `beta_*`, qui n'a pas été appliqué. Il contient clubs, membres/rôles et familles liées, invitations aléatoires expirant après 7 jours, notifications privées, préférences, abonnements push et file de tâches. Les modifications passent par des RPC contrôlées côté serveur, avec RLS et comparaison de révision : un parent peut répondre pour sa famille liée, modifier ses voitures et s'inscrire aux missions sous son nom ; seuls administrateurs/coachs organisent. Les réservations du mode `pool` sont communes et la capacité est vérifiée en base. La création d'un club ajoute seulement des catégories ; aucune personne fictive. `tests-backend.sql` a passé ses assertions sur la vraie base avec les rôles `authenticated` et `anon`, dans une transaction entièrement annulée : accès et isolation, permissions, capacités, validation, notifications et refus d'une révision périmée. Aucun compte de test ne persiste. Les advisors n'ont retourné aucun avertissement/erreur de sécurité ; seuls deux INFO de RLS sans politique concernent les tables privées volontairement fermées et des INFO signalent des index encore inutilisés dans cette base neuve.

Contrat principal : `create_lumo_club(p_name,p_display_name)`, `join_lumo_club(p_code,p_display_name)`, `lumo_context(p_id)` et `save_lumo_club(p_id,p_expected_revision,p_payload)` renvoient `{club,payload,revision,membership,memberships,notification_preferences}` ; `memberships` contient tous les comptes pour un administrateur et uniquement son propre compte pour un parent. Autres RPC : `lumo_create_invite`, `lumo_set_member_access`, `register_lumo_push`, `unregister_lumo_push`, `lumo_set_notification_preferences`, `lumo_mark_notification_read`, `lumo_test_notification`. Le frontend doit encore être vérifié avec l'ensemble de ces contrats et de vrais comptes humains. Le worker push, ses secrets Vault, le cron et les rappels sont un chantier séparé (`supabase-push.sql` si fourni) : leur déploiement n'est pas confirmé par ce document. La réception sur un téléphone réel n'a pas été testée. Les tests de révision ont vérifié un conflit logique ; aucun test de charge avec deux sessions simultanées n'a été effectué. Ne rejouer pas tout `supabase.sql` sur cette base : les tables existent déjà. Aucun secret Supabase/service-role n'est contenu dans les fichiers.
